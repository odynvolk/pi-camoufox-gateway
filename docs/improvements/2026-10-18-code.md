# Code and correctness improvements

Correctness, attribution, and lifecycle. Capability/roadmap material lives in
[2026-10-18-functionality.md](./2026-10-18-functionality.md).

**Everything below is open.** Each item was read out of the source, not inferred. Fixed items are
deleted outright — no "done" markers, no summaries of what shipped. This file tracks what is still wrong;
what landed, and how, is in commits and pull requests.

Labels are stable but **not reserved**: a gap means the item was fixed, not lost. Section A is now gone
entirely — A.3 and A.5 closed here, and A.1, A.2 and A.4 were already gone when this file was written —
and there is no section D, E or H, and no B.1–B.4 or G.1–G.4. B.5 and B.7 are gaps now too, both closed
on the branch named after them — one still cites its label from `tests/snapshot.test.mjs`, the other from
`src/gateway.ts`, which is exactly why the numbering does not move. Renumbering the rest would break
references to these labels that already sit in `src/` comments, commit messages and review threads — so
the gaps stay visible rather than closed.
B.6, B.8, B.9 and G.5 are the later findings still open, added while fixing other items; B.7 was raised the
same way and closed by the suite written for it. G.5 is what survived of a
four-item section: three of those four described code that no longer existed, or asked for something
already true — deleted with the rest, and worth knowing because an item nobody re-reads is an item
someone eventually "fixes" twice.

**On refs:** a ref here is a path and a fragment of the code it means — `` `src/gateway.ts` → `destination_unreported` ``
— and `tests/improvement-refs.test.mjs` greps every fragment out of every file it names. They used to be
line numbers, and that is why they rotted twice inside this file's own lifetime: any commit adding a line
moves every ref below it, and a drifted number still reads like a citation — measured, four of them did,
and one had been pointing at a blank line since the file was written. A fragment survives a move and dies
on a rename, which is the only one of those two a reader can do anything about. So the numbers were
deleted rather than re-pointed, and this paragraph is now a test instead of a promise.

**Grouping principle:** the items are *not* ordered by severity of code smell — they're ordered by
whether a wrong answer here misleads a reader, a model, or a future maintainer. The recurring defect
in this set is not bugs; it's **statements that are slightly stronger than the code behind them.**

## B. Error attribution — faults labelled as something they aren't

### B.6 An engine that restructured organic results only is reported as having answered with nothing

`classifySerp` needs `blocks.length === 0` before it will say `parse_error`. So a *partial* restructure —
the accessibility tree still emitting `link` blocks for the engine's chrome, organic results moved to a
node type we do not read — produces links, no organics, and `empty_results`: "the engine returned no
organic results for that query", when our parser went blind. Note what is *not* wrong here: the chain
does fall through, because `empty_results` is not in `TERMINAL_CODES` (`src/engines/chain.ts` → `const TERMINAL_CODES`), so one blind
adapter is recovered and the model still gets duckduckgo's answer. Two blind adapters is a confident
wrong answer.

The obvious predicate is "links found, none of them clickable", and it was tried against the recorded
pages before being rejected here, which is why it is not in the code:

- it does not fire on the case it is for — chrome links have urls. `serp-no-results.txt` is 4 blocks,
  2 of them `https://` (Preferences, ServiceLogin), 0 organic: the exact shape, and it stays
  `empty_results`;
- it misfires on the shape duckduckgo actually serves — of 78 blocks on `serp-duckduckgo.txt`, 38 carry
  relative urls (`/`, `/compare-privacy`) and match no scheme. An engine whose organics vanished while
  its relative chrome survived would be reassigned to `parse_error`, blaming our parser for a page it
  parsed correctly. That is the false-positive family recorded in
  `docs/solutions/integration/wall-detection-must-be-structural.md`.

What would settle it is a positive signal for "this was a results list", the way `organicResults`' own
filters are positive signals — a count of *expected* node types, or a wrapper-url count, or the
`/url`→result ratio the page used to have. That is a new predicate with its own false-positive budget,
not a widening of this one.

**A recorded instance now exists, and no test reads it as a SERP.** `serp-duckduckgo-html.txt` is 26 link
blocks, every one of them carrying a `/url`, and **not one of them is absolute**: 24 are
`//duckduckgo.com/l/?uddg=<percent-encoded target>&rut=<hash>` wrappers, one is `/html/`, one is
`//duckduckgo.com/feedback.html`. Those 24 are the organic results — the destination is right there,
encoded — and every one is discarded, so `blocks.length` is 26, `results.length` is 0, and the page
reports `empty_results`: "duckduckgo returned no organic results for that query". A tree we refused to
read, blamed on a query.

**The cause is the scheme guard.** `organicResults` drops anything without a scheme before it asks what
engine it is looking at — `src/snapshot.ts` → `if (!url || !/^https?:\/\//iu.test(url)) continue;` — and a
protocol-relative value cannot match that. Measured: 0 of the file's 42 `/url` lines pass, and
`parseSerp(…, "duckduckgo")` returns 0 results. It is the same mechanism already written down for the
sibling fixture in `isChrome`'s own docstring — refused "at its scheme guard, before `isChrome` is
reached" — and it is why the relative-url false positive above bites at all.

**The cause recorded here on 2026-10-23 was wrong, and so was the fix with it.** That version said the
organics vanish "not because the parse failed" but because of an asymmetry in `isChrome` — the `google`
branch exempts a wrapper (`!isWrapper(url)`), the `duckduckgo` branch returns true for any
`*.duckduckgo.com` host — and prescribed giving the duckduckgo branch that exemption. Checked against the
function it named: false. The scheme guard rejects all 26 first, so `isChrome` is never reached for any
of them, and an exemption inside it cannot change this page. Run, not reasoned: with the exemption added
the fixture still parses to 0. It is a no-op twice over, because even where it *was* reachable it
exempts nothing — `isWrapper` only recognises `google.com/goto?url=` and `google.com/url?url=`, so a
duckduckgo wrapper is not a wrapper to it, and the exemption would need `isWrapper` generalised first.
Kept visible rather than quietly rewritten: the next reader who compares those two branches will reach
for the same cause, and should find it already tried.

**The asymmetry is real, and it is a second blocker rather than this one.** Not an inference this time —
a measurement. Make the 26 urls absolute (`https://duckduckgo.com/l/?uddg=…`, nothing else changed) and
they clear the scheme guard, and the page still parses to **0**: the host rule discards them on its own,
because a duckduckgo wrapper *is* a duckduckgo host. Reroute those same wrappers to a foreign host and
the same page parses to **10**. Two independent conditions stand between this fixture and results, and
neither one is enough alone — which is also why relaxing the guard by itself changes nothing: accept
`//…` without giving it a base and `new URL()` throws inside `isChrome`, whose `catch` answers `true`.

**Latent, and still latent.** We request `duckduckgo.com/?q=`, not the html host — and the live recording
`serp-duckduckgo.txt` carries its organics as absolute non-duckduckgo urls, which is why 19 of them
survive today. The only absolute `duckduckgo.com` urls anywhere in `tests/fixtures/` are that page's 15 —
its y.js ad proxy, /updates, /bangs, start.duckduckgo.com — every one of them chrome, every one
correctly dropped. Nothing has been observed failing this way; a redesign of the html host is what would
reach it, which is the exact scenario this item describes.

Three predicates measured against it first, all rejected — recorded because the item previously had no
cases to measure anything against, which is how the "links but none clickable" idea got through once:

| signal | google | duckduckgo | the html case | no-results | wall-consent |
| --- | --- | --- | --- | --- | --- |
| link blocks with a `/url` (status quo) | 10 / 18 | 78 / 78 | 26 / 26 | 2 / 4 | 3 / 3 |
| link blocks with a `/url` **and** nested text | 10 | 5 | **0** | 0 | **2** |
| `/url` lines per link block | 0.56 | 1.0 | 1.0 | 0.5 | 1.0 |

Row 2 is the one that looks right and is not: it finds 5 of duckduckgo's 19 real results, misses the case
it exists for entirely, and fires twice on a consent wall. Row 3 separates the two only by a threshold,
and scores a wall the same as a results page. All three rows were re-measured for this correction and
still hold; what was wrong above was the *cause*, not the table.

**What a fix has to carry — two changes, and neither is a one-liner.**

- A base to resolve against. `organicResults` is handed blocks and an engine name, never the snapshot's
  own url, so it has nothing to resolve `//host/…` or `/html/` *with*. Threading the page url down is the
  actual work here, and the scheme guard is not merely strict: it is what keeps `new URL()` from throwing
  on every one of these values.
- A wrapper exemption that can see a duckduckgo wrapper, i.e. `isWrapper` generalised to `/l/?uddg=` —
  not the same predicate applied to a second branch, which is the no-op above.

Both re-measured against the table with the exemption on, to prove `Preferences`/`ServiceLogin` — the 2
absolute urls of the 4 blocks in `serp-no-results.txt` — still do not become results. Measured in a
scratch tree with both changes: this fixture parses to 10 results (the 24 wrapper lines are 10 distinct
targets), and nothing else moves — `serp-google.txt` 10, `serp-duckduckgo.txt` 19, `serp-no-results.txt`
0, `wall-consent.txt` 0.

### B.8 A page that says we were blocked is reported as a search that returned one result

`tests/fixtures/serp-reddit-blocked.txt` is a recording of a refusal taken from the live gateway through
the `@reddit_search` macro, not a page written to make a point. It is 265 chars and one ref: an image, the
sentence *You've been blocked by network security. If you think you've been blocked by mistake, file a
ticket below and we'll look into it.*, and one link, `File a ticket`, to Reddit's support-desk ticket form.

Measured against it, as the engine that served it would be classified:

```
classifySerp(recording, "google")      →  { kind: "results", results: 1 }
detectWall(recording)                  →  null
classifySerp(recording, "duckduckgo")  →  { kind: "results", results: 1 }
```

The model is told the search succeeded and got one result, and the result is a link to a ticket form on a
page whose own text says access was refused.

**Two rules meet to produce it, and neither is wrong alone.** The block page has one link block, and its
`/url` is `https://support.reddithelp.com/…`, so `organicResults` admits it at its scheme guard
(`src/snapshot.ts` → `if (!url || !/^https?:\/\//iu.test(url)) continue;`) and then asks the only question
it knows how to ask — is this the engine's own page. For google, chrome is decided by host alone
(`src/snapshot.ts` → `if (!host.endsWith("google.com")) return false;`), and the rule for "ours" is
`endsWith("google.com")`. `support.reddithelp.com` is not google.com, so a support desk on a refusal page
**is** an organic result. It is the cost `isChrome`'s docstring records as accepted when the title list was
retired — a foreign host under a chrome-shaped title is a result — one step further: here no title is
needed at all, because the host rule decides alone, and a refusal page's help desk is never the engine's
host.

**`detectWall` does not catch it, and not for the reason this item first stated.** Measured: `null`. The
structural branch bails on its **first** condition — the page has no `heading` line at all, and the rule wants
exactly one at level 1 — so it never reaches the `/url` guard, which is where this item originally said the
miss came from. Deleting that guard changes nothing here: the retry-affordance condition fails too, with no
`Try Again` or `Reload` anywhere in four lines. **No page in the repo, old or new, is missed by the `/url`
guard alone.** Neither phrase list carries "blocked by network security" either, so nothing is claimed and the
page reaches the parser clean. The parser's only question is whether anything looked like a result, and one
thing did.

**The wrong verdict here is the kind the chain cannot walk away from.** `kind: "results"` is what
`src/engines/chain.ts` → `tried.push({ engine: engine.name, code: "ok", message: "served" })` credits as an
engine answering, so no second engine runs. This is the mirror image of B.6 and the opposite of its
consequence: B.6's engine is blind and says `empty_results`, which is not in `const TERMINAL_CODES`, so the
chain hops and the model still gets duckduckgo's answer. This one answers confidently and ends the search.
A parser that went blind is recovered; a refusal read as a result is not.

**Two items merged this week, and this is where both of them land.** The page has a result on the *first*
look, so `src/engines/settle.ts` → `serpWorthAnotherLook` stops the loop at once and
`src/settle.ts` → `polled: false` is what the store gate reads
(`src/tools/search.ts` → `shouldStore: () => !pagePolled`). That gate exists to hold a page that had to be
waited for out of the cache, and it waves this through, because "it answered on the first look" is the
condition it reads as finished. So the value is stored under the search key, which deliberately excludes
`n`, and served for `src/config.ts` → `serpMs: 30 * 60 * 1000`; and the stop-at-first-results rule
shipped as 1.6 means nothing looks at the page again. Measured end to end against
`tests/helpers/fake_gateway.mjs` with this recording as the served SERP: the chain records one step,
`google: ok`; the second identical query costs **0** gateway calls and reports `fromCache`. **A refusal
becomes a cached answer for half an hour, under a key that covers every result count that query is ever
asked for.**

**The recording is one instance; the class is every interstitial with a way out.** Any substituted page
whose sole link points off-engine reports as a successful search: a WAF page with a "contact us", a
rate-limit notice with a status link, a "verify you are human" screen with a help article. The engine
argument does not save it — measured on both, and the `duckduckgo` verdict is the same, because the host
rule only decides which host counts as ours. It is squarely B-family: a fault labelled as something it is
not. B.6 covers results that exist and are missed; nothing here covered a non-result counted as one.

**What a fix has to survive, and no threshold here is invented well enough to skip it.** A predicate that
reclassifies a page as a refusal is keyword or shape evidence over fetched text, which is the exact family
`docs/solutions/integration/wall-detection-must-be-structural.md` records as already having failed once —
a GitHub README that mentions a captcha was refused as a wall, and the fix was to take structure instead of
prose. It has to be measured against the recorded pages the way B.6's three candidates were, and its budget
runs in both directions: the 10 results of `serp-google.txt` and the 19 of `serp-duckduckgo.txt`, each
parsed as the engine it was recorded from, must stay results — and a real results page that also carries a
help or feedback link must not be reduced to a refusal. Whatever it decides has to be a verdict at the
classifier rather than a rule sitting above it, because that is where the two halves of this are one
defect: an error out of `classifySerp` is a code the chain hops on, and a throw is never kept —
`src/cache.ts` → `Failures are never stored.`

### B.9 The gateway reports which engine answered, and we never read the field

One `POST /tabs/{tabId}/navigate` is what `src/engines/google.ts` → `const MACRO = "@google_search"` costs
us: one request in, one page out. On the live gateway — 1.18.1, probed for this item — that request came
back answered by a different engine:

```json
{ "ok": true, "tabId": "…", "url": "https://duckduckgo.com/?q=expressen", "refsAvailable": true,
  "httpStatus": 200, "navigationOk": true, "searchEngine": "duckduckgo", "fallbackFrom": "google" }
```

Reproduced twice, in two sessions, on two different queries. The macro is not the cause:
[macros.js](https://github.com/jo-inc/camofox-browser/blob/v1.18.1/lib/macros.js) maps `@google_search` to
`https://www.google.com/search?q=…`, and that line is byte-identical at `v1.14.0`, `v1.15.0`, `v1.16.0`,
`v1.17.0`, `v1.18.0`, `v1.18.1` and `master`.

**The substitution is decided gateway-side, inside the one call, with nothing of ours in the room.**
[lib/search-fallbacks.js](https://github.com/jo-inc/camofox-browser/blob/v1.18.1/lib/search-fallbacks.js)
returns duckduckgo then bing for `@google_search`, and nothing for any other macro.
[server.js](https://github.com/jo-inc/camofox-browser/blob/v1.18.1/server.js) runs that list after the
google navigation, and the branch we hit logs *"google search returned no organic results; using fallback"*
before re-navigating. One call is still one call to us, so `src/engines/chain.ts` records a single step for
what may have been three navigations, and the page handed to `classifySerp` is one nobody here asked for.

Two facts about that branch, because both are load-bearing below.

- The **check** is gated on the destination (`isGoogleSerp(tabState.page.url())`) and the **fallback list**
  on the macro. A hand-built google url therefore gets the same verdict with nothing to fall back to, and
  answers `{ok: false, googleResultsAvailable: false, searchFallbackAttempted: false}` — seen, four times.
  The macro is the only thing that buys the fallback chain.
- Three separate sites reach that code, and only one of them is the organic-results branch; the other two
  fire when the navigation to google *threw*. So the two fields say "a fallback answered", which is none of
  "google had no results", "google did not load", and "google walled us".

**We read neither field.** `src/gateway.ts` → `export interface NavigateResult` declares one member, `url`,
and `asNavigateResult` reads `body.url` and returns — so there is no third member to reach, and nothing
downstream has a way to ask. Two of the same response's other undeclared fields do have a case:
`tests/gateway.test.mjs` → `nor is a string the gateway saying this was a SERP` asserts `refsAvailable` and
`googleSerp` arrive as nothing. These two have no case, and no name in the type to arrive under.

So the page is classified under the name we asked for. `src/engines/google.ts` →
`settledSerpVerdict(context, tab.tabId, "google")` is the only thing between the navigation and the parser,
and that literal is what `src/engines/settle.ts` passes to `classifySerp`.

**Measured on the recording of exactly that page** — `tests/fixtures/serp-google-answered-by-duckduckgo.txt`
(18 609 chars, 18 807 bytes; 160 non-ASCII characters, 122 at two bytes and 38 at three, which is the
198-byte difference exactly — Swedish `ä å ö` in the page's prose and the tree's own `’ • ›` punctuation):

| engine passed to `classifySerp` | results |
| --- | --- |
| `"google"` — what the extension actually passes | **30** |
| `"duckduckgo"` — what actually answered | **22** |

The 9 that only `"google"` yields are DuckDuckGo's own footer, delivered as search results:
`https://start.duckduckgo.com/`, `https://duckduckgo.com/updates`, `https://duckduckgo.com/compare-privacy`,
`https://duckduckgo.com/bangs`, `https://duckduckgo.com/duckduckgo-help-pages/`,
`https://duckduckgo.com/pro`, `https://duckduckgo.com/email`, `https://duckduckgo.com/newsletter`,
`https://duckduckgo.com/collaborations`. Mechanism: `src/snapshot.ts` →
`if (!host.endsWith("google.com")) return false;` — a DuckDuckGo link is, by that rule, an unaffiliated
organic result. One result moves the other way: a `play.google.com` link is chrome under `"google"` and an
organic result under `"duckduckgo"`. Both directions are committed by
`tests/snapshot.test.mjs` → `B.9 as filed:`.

It is B.8's mechanism one stage earlier, and B.8's item already names the rule that does it — the host
rule decides alone. B.8 is one off-engine link becoming the only result on a page that refused us; this is a
whole page from another engine, read as ours.

**Not a one-off. The same flip is already measurable on a fixture this file has been arguing with since
B.6.** `serp-duckduckgo.txt` parsed as `"google"` returns **29** where it returns **19** as
`"duckduckgo"`: 11 blocks cross the line, 9 of them the identical footer urls above and 2 the ad
proxy B.6 enumerates as "every one of them chrome, every one correctly dropped". Correctly — under the
engine that answered.

**The trigger is not "Google had nothing", which is what makes this arrive on good searches.** Six google
navigations were run against the live gateway for this item — two through the macro, four at hand-built
google urls — in five sessions, and every one of them was reported as having no organic google results. One
of the four, `https://www.google.com/search?q=expressen`, served a complete results page: heading
`expressen - Sök på Google`, seven organic results behind `google.com/goto?url=` wrappers, a
*People also ask* block, and a pagination `Next` — and the call still answered `ok: false` with
`googleResultsAvailable: false`.

Running the gateway's own predicate against that rendered page says why. Transcribed from
[lib/google-serp.js](https://github.com/jo-inc/camofox-browser/blob/v1.18.1/lib/google-serp.js) and
evaluated in the page: `#rso` present, `#search` present, 12 `h3` inside them, **0** counting as organic —
identical immediately and four seconds later, so not a race. Of the 12, six resolve to
`google.com/goto?url=…` and one to `play.google.com`; the predicate requires a host that is *not* google's.
Five have no anchor ancestor at all. A SERP whose organic titles are wrapped in `google.com/goto?url=` has
no organic results by that test — which is the exact shape `CONTEXT.md` calls a **goto URL** and
`organicResults` already carries a `resolvable` flag for.

So on this host the `google` engine is a request for google that usually returns a DuckDuckGo page, and the
substitution is not preceded by an empty Google. It is upstream's probe and upstream's fix; nothing in this
repo reaches either. Everything below is what is ours.

**`chain.ts` is thereby partly redundant, in the direction that matters.** Our second hop exists because
google might not answer. By the time the first hop returns, duckduckgo may already have been tried and
accepted upstream, and then bing. `src/engines/chain.ts` → `const TERMINAL_CODES` has no member meaning "a
different engine answered upstream", because until now no answer we get could carry that. What `tried`
records for the single step is `src/engines/chain.ts` →
`tried.push({ engine: engine.name, code: "ok", message: "served" })`.

**`empty_results` from `"google"` may be DuckDuckGo having nothing to say.** The code path is plain: an
engine name is a string into `classifySerp`, whose error branches all interpolate it —
`src/snapshot.ts` → `returned no organic results for that query` — so a substituted page with nothing
organic in it yields a message attributing DuckDuckGo's emptiness to google. That is a different
instruction to a model. "Google has nothing on this" says go elsewhere; "DuckDuckGo has nothing on this"
says the query is the problem — and the next hop then asks DuckDuckGo again, which is the one thing a model
cannot infer from the first message.

Seen, it went the other way, and that is the worse direction. Neither substituted page came back empty. The
`expressen` page parsed to 22 as `"duckduckgo"` and 30 as `"google"`, and a deliberately meaningless query
(`zzqxv plmunktorv 91827`) fell to DuckDuckGo too and parsed to **21** results under `"google"`: a
parts-catalogue page that matched the digits, three SEO listicles about torrent sites, and 11 of
DuckDuckGo's own promo links. `empty_results` would have been the honest answer. What a model gets is 21
results and `(via google)`.

**1.4's mechanism is what is confidently wrong.** `src/tools/search.ts` → `Name the engine that answered` is
the rule the header is built on, and `README.md` → `The header names the engine the tool selected` is how
that rule reaches users. The word doing the work is *selected*: the name printed is the engine we asked for,
and the page can be another engine's. The distinction 1.4 was built to draw — "google served this" and
"duckduckgo served this after google walled" being different claims about the same links — is drawn in the
right place from the wrong input, and no value this client reads can tell the two apart.

**The version gap, stated carefully.** Our recorded contract is 1.14.0 across 36 paths
(`tests/fixtures/openapi.json` → `"info"`); the live gateway is 1.18.1 across 38, the two extra being
`/tabs/{tabId}/select` and `/tabs/{tabId}/fetch-current-resource`. In the recording, navigate's `200` response
is a bare `{"type": "object"}` — a fact the client already leans on at `tests/gateway.test.mjs` →
`declares no fields at all` — so these two fields were never promised *or* denied, and that is why
refreshing the recording, already flagged at
`tests/gateway.test.mjs` → `Refreshing the recording is how that settles`, is load-bearing rather than
housekeeping: against a contract that declares nothing there is no "undeclared" to name, and no way to check
a claim that these fields sit outside it. Refreshing does not settle this item either — 1.18.1 does
enumerate navigate's response (`ok`, `tabId`, `url`, `httpStatus`, `navigationOk`) and names neither field.
The end state is "outside a declared contract", not "declared".

**Scope, precisely.** The two fields are spread from one local initialised to `null`, so they are present
**only when a fallback fired**: two observed navigations carried them, the four direct-url google
navigations carried neither — they were answered `ok: false` and returned before the response object that
carries the spread is built. Nothing here says every navigate carries them. The success path, where google
does answer, is a different shape again — `{ok: true, …, refsAvailable: false, googleSerp: true}`, also
undeclared and also unread; read out of the source for this item, and recorded once before it, at
`tests/helpers/fake_gateway.mjs` → `are deliberately unmodelled`. No google navigation run here got there.

**And the engine we refuse is the one it falls back to.** `engine: "bing"` is refused today, and the refusal
is worth quoting as the code writes it rather than as anyone summarised it. `src/config.ts` →
`export const ENGINE_NAMES = ["google", "duckduckgo"] as const;` makes `isEngineName("bing")` false, so
`src/tools/search.ts` takes the unknown-name branch and throws `unsupported` reading
`unknown engine "bing" (string) — known: google, duckduckgo`, before any tab opens —
`tests/search-tool.test.mjs` → `an engine we have no adapter for is refused as an unknown name`. It says
*unknown*, deliberately not *unavailable*: the "disabled in your config" wording is held back for a name
that is real and switched off, and the reason written for that split, at `src/tools/search.ts` →
`setting that does not exist.`, is that merging the two sends a model hunting for a setting that has no
existence. `README.md` → `Bing is not offered` is the same refusal stated as a capability rather than as a
name nobody recognises. And [lib/search-fallbacks.js](https://github.com/jo-inc/camofox-browser/blob/v1.18.1/lib/search-fallbacks.js)
navigates to `https://www.bing.com/search?q=…` inside our google call, unasked. A model cannot request a
Bing page and can be handed one.

Two things about that third hop.

- **It is not gated on results at all.** A candidate is accepted when its navigation resolved, the page url
  still carries that engine's host, and the first 1 000 characters of body text match none of
  `captcha`/`verify you are human`/`unusual traffic`. So a Bing page reaches us whenever the DuckDuckGo hop
  throws or is blocked, whatever it is showing. Observed, on the way: the nonsense query above fell to
  DuckDuckGo and was accepted with nothing answerable on it — the second hop passing on navigation alone,
  which is also why the third is reached by DuckDuckGo failing and not by a query being bad enough.
- **What a Bing page does under `isChrome`, where it could be measured.** Three probes at explicit
  `https://www.bing.com/search?q=…` urls on this gateway, every one answered `ok: true, httpStatus: 200,
  navigationOk: true`, and no two of them carry the same page. The first, run for this item
  (`q=expressen`), returned 3 921 chars with nothing organic on it and `classifySerp` called it **9
  results**: Images, Videos, Maps, News, Privacy and Cookies, Legal, Advertise, Help, Europeiskt
  dataskydd. Asked again at that identical url it returned 14 904 chars, ten of them organic, and the same
  call called it **17**. At `q=camoufox anti-detect`: 13 050 chars, **17** again.

  So no count off a Bing page is load-bearing — one url answered 9 and 17 — and none is needed. What no
  probe varies is the code: chrome is filtered by the host of the engine a search asked for, so no
  `bing.com` link is ever chrome under any name, and every count above still carries that engine's own
  navigation and footer. The two later pages agree on the seven links that do it — Bing's own `Web`,
  `Images`, `Videos`, `Maps`, `News`, `Privacy`, `Terms` — and each of the three counts is identical under
  all four engine names tried: `"google"`, `"duckduckgo"`, `"bing"`, `""`. On both of those later pages
  every organic row takes its title from the block's first link, so ten results come back named for the
  domain alone, each behind a `bing.com/ck/a` wrapper no `resolvable` flag covers.

  None of the three is committed as a fixture, deliberately. The page is what moved at a fixed url, so an
  assertion written against one of them reddens with nothing broken, and
  `scripts/record-fixtures.py` names `serp-bing.txt` among its targets and re-records it on demand — the
  next recording would disagree with the assertion. What the mechanism costs is instead pinned where it is
  ours: `tests/snapshot.test.mjs` → `B.9 as filed:`, a substituted page read under the wrong engine name.

  That is not four branches agreeing, it is three branches and two rules. The fallback branch,
  `src/snapshot.ts` → `return host.endsWith("google.com") && !isWrapper(url);`, cannot answer differently
  from the google branch: for any host, `if (!host.endsWith("google.com")) return false;` followed by
  `return !isWrapper(url)` reduces to exactly it. Measured, the two give the same count for every one of
  the 12 files in `tests/fixtures/`, and the same count on each of the three live Bing pages. Neither rule
  knows Bing's chrome, and a third branch that copies the first changes nothing about the outcome. It is
  also unreachable from production as things stand: `classifySerp` is only ever reached through
  `settledSerpVerdict(context, tab.tabId, "google")` and its `"duckduckgo"` twin, so a Bing page that
  arrived would be filtered by whichever engine we asked for, not by being Bing.

  Not reproduced: a bing *fallback* firing. Getting there needs the DuckDuckGo hop to fail, and nothing
  about a query controls that — the nonsense query fell to DuckDuckGo and DuckDuckGo passed. So "we refuse
  to offer the engine the gateway is willing to answer with" is reproduced, and what a Bing page does once
  it is here is measured three times at pages that do not repeat. The refusal, the arrival, and the count
  on arrival are three separate claims, and only the first is a decision this repo made.

**What a fix has to carry.** Four things, and the first one alone invites stopping early.

- The read itself is one field on one interface and it is the cheapest link in the chain: the gateway has
  already decided, has already said it, and `asNavigateResult` is where the fact dies. Reading it changes no
  behaviour on its own — which is exactly what makes it tempting to stop there, and what follows is why
  that would be a mistake.
- An engine name from config and a page that arrived from a navigation are two different facts, and
  `Engine.name` currently stands in for both. Whatever carries the substitution has to say whether it moves
  `chain.ts`'s credit, the per-result `engine` field the cache stores, or only what the model is told. All
  three are reachable from one value and they are not the same decision:
  `src/engines/types.ts` → `Which engine is credited is decided by the chain from` is a deliberate choice
  with a reason attached, and it survives only if the fix argues with it.
- It overrules a note written for the opposite purpose. `tests/helpers/fake_gateway.mjs` →
  `are deliberately unmodelled` explains why the fake sends `refsAvailable` and `googleSerp` while our type
  carries neither, and closes by saying they are there to prove we ignore what we do not model — not to be
  completed by adding them back. Adding fields to `NavigateResult` is what this fix is, so that sentence is
  in the way on purpose, and its two reasons part: one is answered by refreshing the recording, and "nothing
  reads these" is the claim this item exists to retire.
- It has to survive the field's own weakness: two names that say *a* fallback answered, from three different
  causes, present only when one fired. A line that paraphrases `fallbackFrom: "google"` as "Google had
  nothing" would be a fresher edition of the defect it is reporting. And `googleSerp` is the third state —
  google did answer — reported on the one path nobody reads.

**Why the pin sits one step away from the defect.** `tests/snapshot.test.mjs` → `B.9 as filed:` pins
`classifySerp`: a page in one hand, an engine name in the other. That is the whole of what is reachable
without writing production code, and this branch writes none. The defect itself is one call site earlier, at
a field nothing reads, and no assertion can exercise a read that does not exist. Read the pin as the weaker
claim it is: the damage is load-bearing and stays load-bearing across the change, and that is not the same as
the fix landing.

## C. Guard-surface correctness

The address guard is the most carefully built thing in this repo (see `CONTEXT.md`). These are the
places where it's narrower or blunter than it appears.

### C.1 `blockedHosts` cannot express path, port, or scheme

Only lower-cased host equality and `*.suffix`/subdomain matching (`matchesHostRule`,
`src/net-policy.ts` → `function matchesHostRule`). There is no allowlist at all — refuse only.

Two consequences worth stating in the docs:
- it is applied to **destinations**, so it cannot filter a blocked host out of **search results** —
  a blocked host still appears in search output;
- a rule can't express `example.com/admin` or `:8080`, which is where "block that tool's UI but not
  its docs" requests will go.

### C.2 `destination_unreported` fails *every* read, not just risky ones

When `policyCanRefuse` is true, a snapshot reporting no destination throws unconditionally
(`src/gateway.ts` → `destination_unreported`). The fail-closed choice is right and the reasoning in `CONTEXT.md` is sound —
but the blast radius is total: **a gateway upgrade that stops reporting `url` on `/snapshot` turns
all reads into errors** until the user opts out of the guard.

What this asked for was (a) a doc note and (b) the gateway's own state in the message. Both are settled,
differently. (a) — `README.md` → `Refuses to return a page` says it, and so does the refusal: the
`destination_unreported` advice line (`src/extension.ts` → `Upgrade it`) names the gateway's silence and tells
the user to upgrade it, which is the sentence this item wanted. (b) — the `/health`-style status now ships,
and is deliberately *not* attached to this code: `destination_unreported` is not on `DIAGNOSED_CODES`, and
the one fact a diagnosis could add here, that a browser is there, is already settled by a page having come
back.

What is still wanted is the version, and that is not ours to give: no gateway response reports one, so the
only version this repo holds is the recording's own (`tests/fixtures/openapi.json` → `"info"`). The user is
told to upgrade and not what they are on. §2.3 calls itself the only Tier-2 item that is a genuine
gateway-version dependency — this is a second one, and the blindness is ours.

### C.3 The stray-tab sweep's safety condition is also its blind spot

With a sibling open in flight it filters strictly by url (`src/gateway.ts` → `redirect wrapper cannot`), and the code states
plainly that "a redirect wrapper cannot" match that way. So a lost response during concurrent
activity can still leave a tab behind, reclaimed only at `session_shutdown`. Known, documented,
acceptable — recording it so nobody "fixes" it by loosening the filter, which is the dangerous
direction.

## F. Cache semantics

### F.1 Eviction is insertion-order, not LRU, at 128 entries

`src/cache.ts` → `export const MAX_ENTRIES`. A re-read key keeps its original slot and can be evicted first. **Pinned as
intentional** by `tests/cache.test.mjs` — "eviction drops the oldest inserted key, not the least
used".

Deliberate is fine; surprising is not. At minimum document the choice where users can see it. If the
cache grows past a few entries of real traffic, this becomes the reason hit rates look random.

### F.2 Cache is per-pi-session — nothing shared, nothing surviving a restart

`src/camoufox-gateway.ts` → `const extensions = new Map`. Two concurrent pi sessions asking the same question each pay the
full browser round trip. Fine for a per-session design; worth an explicit statement of intent,
because "why doesn't the second session get my cache?" will otherwise read as a bug report.

## G. Robustness and parsing

### G.5 Locale is not controllable

Recorded results arrived Swedish (`Sök på Google`), which is a gateway-side reality with nothing on this
side translating it. The macro takes only a query, so no `hl`/`gl` parameter can be attached to it from
here. DuckDuckGo is the half that is reachable: this code builds that url (`src/engines/duckduckgo.ts` → `const SEARCH_URL`),
so a locale parameter is available there and unused.

Left open because the asymmetry is the whole design question, not the parameter. Pinning one locale for
one engine and not the other makes the two engines' pages differ in a way no caller can ask for or
notice, and a `locale` setting nobody can honour on the primary engine is a setting that lies. The
gateway owning the request is the argument for asking for one there instead.

Note what is *not* open: filtering chrome no longer depends on titles at all, so a Swedish page no
longer needs a Swedish entry anywhere in this repo (`isChrome`, and the measurement recorded there).

## Recommended order

1. **B.9** — the only open item where the fact is already in a response and merely not read, so the first
   step is a field on an interface rather than a new predicate with a false-positive budget to earn. Not a
   one-liner for all that: the three constraints closing the item are the work, and the pin retires with
   them.
2. **C.1, C.2, C.3, F.1, F.2, G.5** — document the intent. Several are deliberate
   choices whose *reasoning* just needs to reach the people who'll otherwise file them as bugs.
3. **B.6** — only as a positive signal, with the recorded pages as the false-positive budget. The

4. **B.8** — with the same discipline, and none of the measurement done yet: B.6's candidates were tried
   against the recorded pages, and B.8's have not been. Its budget has a second direction B.6's did not —
   a page that both has results and links to help must stay results.
