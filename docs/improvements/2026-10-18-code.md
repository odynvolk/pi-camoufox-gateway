# Code and correctness improvements

Correctness, attribution, and lifecycle. Capability/roadmap material lives in
[2026-10-18-functionality.md](./2026-10-18-functionality.md).

All 21 items below were read out of the source, not inferred. Line numbers are as of `68d1e14` — except
the eight that point into files the E work edited (`gateway.ts`, `camoufox-gateway.ts`,
`tools/search.ts`), which were re-pointed at the current tree, because a document whose thesis is stale
citations cannot carry its own. Two of those (`search.ts:65`, `camoufox-gateway.ts:47,66`) were already
pointing at the wrong line — one at a blank — before anything moved, so they are now correct rather than
merely shifted. Each was re-verified against the tree at write time. Implemented items are removed rather
than marked; their IDs stay reserved, and any open limitation they carried is promoted to an item of its
own — which is why D.4 and B.5 exist. Three more (B.6, B.7, D.5) were found while fixing other items, so
they are new findings rather than promotions.

**Grouping principle:** the items are *not* ordered by severity of code smell — they're ordered by
whether a wrong answer here misleads a reader, a model, or a future maintainer. The recurring defect
in this set is not bugs; it's **statements that are slightly stronger than the code behind them.**

## A. Claims that outrun the code

These are the highest-priority items in this document, because they pass review and tests — the
claim simply isn't asserted anywhere.

> **A.1** (the dead-gateway liveness guarantee) and **A.2** (`cache.pageMs` had no page-cache
> consumer) were implemented and removed. Their IDs stay reserved so references to them in commits,
> branches and review threads stay addressable.

### A.3 Two archived decisions were reversed without reconciling the docs

| Doc says | Code does |
| --- | --- |
| "Key = normalized query + engine + `resolve`" (`docs/plans/archive/…:236`) | excludes both `n` and `resolve`, caches the raw engine page (`search.ts:105-108`) |
| blockedHosts: "default empty, do not block by default" for private ranges (`…:190-193,218`) | ships `network.allowPrivateHosts: false` — private ranges **are** blocked (`config.ts:72`, documented at `README.md:110`) |

The cache-key implementation is the **more correct** of the two — the doc is stale, not the code.
Worth marking in the archive rather than silently fixing, so the reversal is traceable.

### A.4 The `n`-below-one message blames the engine

`n: 0` or negative → `clamped = Math.max(1, Math.min(requested, 10)) = 1` (`search.ts:104`), then
`formatResults` prints:

> (clamped to 1: **the engine returns a page of 1**; narrow the query for a different page)

The engine returns a page of 10. **The clamp is ours.** The behaviour is correctly disclosed —
`tests/search-tool.test.mjs:125` pins *"n below one is disclosed, not silently turned into a single
result"* — only the *explanation* is wrong, and it's wrong in the direction of sending the model off
to narrow a query that didn't need narrowing. One branch fixes it: distinguish "clamped by us" from
"engine page is genuinely narrow".

### A.5 Search output doesn't say which engine answered

`(via <engine>; tried …)` appears only when `tried.length > 1` (`search.ts:65`). A first-try Google
success never names the engine in model-facing text. Related: `engine?` is a free-form string, not an
enum (`camoufox-gateway.ts:23`), so `bing` yields *"not available (enabled: google, duckduckgo)"*
with no mention of *why* it was dropped — that reasoning exists only in prose.

Both are one-line fixes; see functionality doc §1.4 for the *why it matters*.

## B. Error attribution — faults labelled as something they aren't

> **B.1–B.4** (the `gateway_error` catch-all, the defaults-only gateway url in failure output, the
> unvalidated `schema`, and the call-order coupling between `empty_results` and `parse_error`) were
> implemented and removed. Their IDs stay reserved so references to them stay addressable.
>
> What landed: `internal_error` now covers any throw we could not classify, at the source rather than
> at the boundary (`errors.ts`, `session.ts`, `extension.ts`); failure output quotes a gateway url only
> when a config actually loaded it (`camoufox-gateway.ts`); a `schema` that cannot address anything is
> refused as `unsupported` before the navigation — for having no usable `x-ref`, or for a `type` the
> recorded contract does not allow (`tools/read.ts`); and `classifySerp` (`snapshot.ts`) owns the
> ordering that used to be duplicated across both engine adapters, with every branch asserted together
> in `tests/snapshot.test.mjs`.
>
> The `type` half is worth flagging: it was missing from the first cut of this fix, which meant a
> natural schema typo — assuming `type: "object"` is implied by there being `properties` — still cost a
> tab, a settle loop and a close, and arrived as `gateway_error`. The guard's own doc and the README both
> claimed a pre-navigation refusal the code only partly performed — the defect this document is about,
> installed by the commit that was fixing it.

### B.5 A browser error page past the interstitial threshold is not classified at all

`detectWall` gates its phrase evidence on `INTERSTITIAL_MAX_CHARS`: a browser's own error page under
that size comes back as `navigation_failed`, and a wider one is returned as page text, which is the
shape of every false-negative this file has.

On the search path the same page lands as `parse_error` instead — and that one is right by
construction: past `PARSEABLE_MIN_CHARS`, a page with nothing link-shaped in it is a changed tree,
whatever else it mentions. Pinned as such, so nobody reads the width as an oversight.

Left open deliberately. Raising the threshold, or matching error vocabulary anywhere in the body, is
how the GitHub-README false positive happened
(`docs/solutions/integration/wall-detection-must-be-structural.md`), and the failure stays asymmetric:
a wrong wall denies a read that worked, a missed one returns odd text. Closing this wants *positional*
evidence — an error page is one heading, a retry affordance, and almost no refs — rather than a wider
keyword net or a bigger number.

### B.6 An engine that restructured organic results only is reported as having answered with nothing

`classifySerp` needs `blocks.length === 0` before it will say `parse_error`. So a *partial* restructure —
the accessibility tree still emitting `link` blocks for the engine's chrome, organic results moved to a
node type we do not read — produces links, no organics, and `empty_results`: "the engine returned no
organic results for that query", when our parser went blind. Note what is *not* wrong here: the chain
does fall through, because `empty_results` is not in `TERMINAL_CODES` (`chain.ts:26-32`), so one blind
adapter is recovered and the model still gets duckduckgo's answer. Two blind adapters is a confident
wrong answer.

The obvious predicate is "links found, none of them clickable", and it was tried against the recorded
pages before being rejected here, which is why it is not in the code:

- it does not fire on the case it is for — chrome links have urls. `serp-no-results.txt` is 4 blocks,
  2 of them `https://` (Preferences, ServiceLogin), 0 organic: the exact shape, and it stays
  `empty_results`;
- it misfires on the shape duckduckgo actually serves — of 78 blocks on `serp-duckduckgo.txt`, 38 carry
  relative urls (`/`, `/compare-privacy`) and match no scheme. An engine whose organics vanished while
  its relative chrome survived would be reassigned to `parse_error`, blaming our parser for a page it
  parsed correctly. That is the false-positive family recorded in
  `docs/solutions/integration/wall-detection-must-be-structural.md`.

What would settle it is a positive signal for "this was a results list", the way `organicResults`' own
filters are positive signals — a count of *expected* node types, or a wrapper-url count, or the
`/url`→result ratio the page used to have. That is a new predicate with its own false-positive budget,
not a widening of this one.

### B.7 A 400 the gateway sends back about *our* request body is reported as a gateway fault

`httpError` special-cases 401/403, 404 (route or tab), and a 400 whose message mentions a blocked url;
everything else falls through to `gateway_error` (`gateway.ts:717`). A 400 is the status that means
"the request you sent is not acceptable", so every request-body defect the client does not predict is
attributed to the service — the same family as B.1, one layer further out.

B.3's guard closed the reachable instance of it (`tools/read.ts` now validates a `schema` against
`tests/fixtures/openapi.json` before anything is dialled, including `type`). What remains is the
principle rather than a known path: fields the client passes through unvalidated, or a gateway whose
validator is stricter than its own published contract.

Left open deliberately, because the honest relabelling is not obvious. Mapping the remainder to
`internal_error` would say *we* are wrong, which is right about the status code and wrong about the
cause whenever the gateway has drifted from `openapi.json` — and it would move a code users act on
("is this my config or is it the service?"). The gateway's own message is already carried through, so a
reader can see what was rejected. Fixing this properly means naming the rejected field from the client
side, which wants the request bodies typed against the recorded contract rather than assembled inline.

## C. Guard-surface correctness

The address guard is the most carefully built thing in this repo (see `CONTEXT.md`). These are the
places where it's narrower or blunter than it appears.

### C.1 `blockedHosts` cannot express path, port, or scheme

Only lower-cased host equality and `*.suffix`/subdomain matching (`matchesHostRule`,
`net-policy.ts:87-94`). There is no allowlist at all — refuse only.

Two consequences worth stating in the docs:
- it is applied to **destinations**, so it cannot filter a blocked host out of **search results** —
  a blocked host still appears in search output;
- a rule can't express `example.com/admin` or `:8080`, which is where "block that tool's UI but not
  its docs" requests will go.

### C.2 `destination_unreported` fails *every* read, not just risky ones

When `policyCanRefuse` is true, a snapshot reporting no destination throws unconditionally
(`gateway.ts:420-429`). The fail-closed choice is right and the reasoning in `CONTEXT.md` is sound —
but the blast radius is total: **a gateway upgrade that stops reporting `url` on `/snapshot` turns
all reads into errors** until the user opts out of the guard.

This deserves (a) a doc note and (b) the `/health`-style status in the error message, so the user
learns "your gateway version stopped reporting destinations" rather than "reads are broken". Ties
directly to functionality §2.3/§Tier-3 (`/health`).

### C.3 The stray-tab sweep's safety condition is also its blind spot

With a sibling open in flight it filters strictly by url (`gateway.ts:243-247`), and the code states
plainly that "a redirect wrapper cannot" match that way. So a lost response during concurrent
activity can still leave a tab behind, reclaimed only at `session_shutdown`. Known, documented,
acceptable — recording it so nobody "fixes" it by loosening the filter, which is the dangerous
direction.

## D. Session and lifecycle

### D.1 `session_shutdown` tears down *every* session in the process

`camoufox-gateway.ts:138-143` drops every session's client, cache, and gateway session, then clears
the whole map. In a shared-process, multi-session host, **one session's shutdown event kills every
other session's state.**

Highest-consequence item in section D. If pi can host concurrent sessions in one process, this is a
correctness bug, not a robustness nicety — worth confirming pi's lifecycle contract first, since the
fix depends on whether the event is per-session or per-process.

### D.2 `scripts/diagnose-wall.mjs` opens a third session namespace

Hardcoded `userId: "pi-diag"` (`scripts/diagnose-wall.mjs:17,20-21`), separate from the pi-derived
`sessions`. Three namespaces now exist in the gateway's tab list, and the diagnosis tool is the one
that leaves state behind. Minor, but it's exactly the kind of thing that makes a wedged gateway
mysterious.

### D.3 Every tool call pays a preflight round trip

At the start of each 60 s window (`extension.ts:92-96`), adding latency to the first call of each
window **even when the gateway is healthy**. The liveness fix left this untouched — a success is still
cached for 60s — so the two still want a joint decision (e.g. probe-on-launch + background refresh,
rather than probe-at-window-boundary).

### D.4 The 5s failure window is shorter than one probe can cost

At shipped defaults a hung gateway makes the liveness probe itself burn the full 30s `timeoutMs`, so by
the time the next sequential caller arrives the 5s window has already passed — measured: every
sequential call re-dials. The negative failure cache is therefore a **burst** guard at those defaults,
and it is `retry: "connect-only"` on the status probe that bounds the sequential case.

Covering it wants its own knob: a dedicated probe deadline well under `timeoutMs`, so "don't re-ask for
5s" is a promise the probe can actually keep. Same family as D.3 — both are about what the liveness
path *costs*, not what it remembers.

### D.5 Two long pi session ids can share a gateway namespace

`gatewaySessionId` sanitises, prefixes, then `.slice(0, 128)`. The slice is applied to the whole id, so
two ids agreeing on the first 125 characters after sanitising produce the same `userId` — and the
gateway namespaces tabs by `userId`, which is the one thing the module header says the derivation
exists to protect. Found while pinning that function's error path, not from a live fault: pi's own
session ids are UUIDs, well under the limit today, so this is a host-provided-id hazard rather than a
current misbehaviour.

The truncation is pinned by `tests/session.test.mjs`, including the collision, so fixing it is a
deliberate change rather than a silent one. Both fixes are behaviour-visible and therefore out of
keeping with a cleanup: hash the overflow instead of truncating (stable, no collisions, still 128
chars), or refuse an id that would truncate — which turns it into an `internal_error` like the empty
ones, and would need confirming that no host hands out long session ids first.

## E. Config integrity

> **E.1–E.4** were implemented and removed. Their IDs stay reserved so references to them stay
> addressable.
>
> What landed: `search.maxResults` is refused at load unless it is a whole number from 1 to
> `MAX_SEARCH_RESULTS`, which is now declared once in `config.ts` and read by the tool's clamp and the
> parameter description, so a config can no longer say 25 and quietly mean 10; `GatewayClientOptions.timeoutMs`
> is required, which deletes the client's private `?? 30_000` and leaves the documented default as the
> only one (`gateway.ts`) — pinned end to end through `pi.registerTool`, since 27 of 28 call sites
> already passed it and the fallback was never the effective value; `read.maxCharsCeiling` (40 000)
> bounds what one call may ask for and reports `cappedAt` when it intervenes, with a note that names the
> ceiling instead of offering the parameter that was just capped (`tools/read.ts`, `extension.ts`); and
> no parameter description quotes a number a config file can contradict — they name the key, the way
> `fresh` already did.
>
> Two claims inside those items did not survive reading the code, and are recorded rather than quietly
> dropped. E.4's headline case was already fixed: `n`'s description quoted `MAX_SEARCH_RESULTS`, a
> structural page width, which is a fact whatever the config says — the distinction this branch had to
> *draw* in the test that used to demand numbers for everything. And E.4's "`search.ts` and `read.ts`
> disagree about which wins" was not true: both read the resolved config, so the file value already
> beat the shipped default on both paths. Only the sentence about it was wrong.
>
> A *per-call* `n` could also be fractional, which this note first described wrongly in both directions:
> it claimed the output would read "clamped to 2.5", and `clampedTo` is never set for that case —
> `requested === clamped` when the request is already under the page bound. What actually happened was
> worse: `n: 2.5` sliced to 2 rows and disclosed **nothing**, and on a page of 2 the output said
> "0.5 fewer result(s)". Fixed on this branch — `tools/search.ts` now refuses a non-integer count, and
> `n` is `Type.Integer` in the schema rather than `Type.Number` promising what the code rejects. Refused
> rather than floored, because the only sentence available for a floor is A.4's false one: "the engine
> returns a page of N".

## F. Cache semantics

### F.1 Eviction is insertion-order, not LRU, at 128 entries

`cache.ts:26,33-43`. A re-read key keeps its original slot and can be evicted first. **Pinned as
intentional** by `tests/cache.test.mjs` — "eviction drops the oldest inserted key, not the least
used".

Deliberate is fine; surprising is not. At minimum document the choice where users can see it. If the
cache grows past a few entries of real traffic, this becomes the reason hit rates look random.

### F.2 Cache is per-pi-session — nothing shared, nothing surviving a restart

`camoufox-gateway.ts:47,66`. Two concurrent pi sessions asking the same question each pay the
full browser round trip. Fine for a per-session design; worth an explicit statement of intent,
because "why doesn't the second session get my cache?" will otherwise read as a bug report.

## G. Robustness and parsing

### G.1 Per-engine page width is unaligned

Google pins `GOOGLE_PAGE_SIZE`; DuckDuckGo slices by whatever the page carried
(`duckduckgo.ts:41`). So `shortBy` means something slightly different per engine — and any
cross-engine comparison inherits that drift.

A third number sits over both: the tool's own ceiling, `MAX_SEARCH_RESULTS` (`config.ts`). That one is
single-sourced across the three things that have to agree — the config bound, the clamp in
`tools/search.ts`, the parameter description — but it cannot absorb either engine's width, because only
Google has a width to take. So if the macro started serving 20, the tool would still ask for 10 of it:
not wrong, just leaving 10 unused, and nothing says so. Shrinking the other way is at least disclosed —
a page narrower than requested already surfaces as `shortBy`.

### G.2 Locale is not controllable, and chrome-filtering carries hardcoded titles

Documented as a gateway reality (results arrived as Swedish `Sök på Google`) with no client-side
handling (`docs/brainstorms/…:130`). `CHROME_TITLES` filters chrome by a hardcoded English/Swedish-ish
title list (`snapshot.ts:42-43`), though chrome filtering is stated to be primarily host-based
(`snapshot.ts:134-152`). The hardcoded list is a small, findable maintenance trap.

### G.3 Fixtures are the only defence against engine markup drift

Re-recorded by an out-of-band Python script (`scripts/record-fixtures.py`, documented at
`README.md:167`). Legitimate design, but it means **the parse path has no runtime
degradation story** — when Google changes markup, the failure is user-visible. This is the strongest
code-level argument for the JSON-returning engine in the functionality doc §1.5.

### G.4 `_onUpdate` is unused and there is no `outputSchema`

`camoufox-gateway.ts:95,112`. Consequences: no partial/streaming progress during long settle loops,
and no machine-checkable output contract. Pi supports both (pi's own `docs/extensions.md` — declare
`outputSchema` + return matching `structuredContent` when the result is data).

## Recommended order

1. **D.1** — cross-session teardown, once pi's lifecycle contract is confirmed.
2. **A.3** — reconcile the two reversed decisions; cheap, and it currently misleads readers.
3. **G.1** — page-width drift; wants a test before a change.
4. **A.4, A.5, G.4, H.1** — small clarity fixes, batch them. A.4 is now only the *explanation* for a
   sub-one `n`; the fractional case that used to be lumped in with it is fixed.
5. **C.1, C.2, C.3, D.2, D.3, D.4, F.1, F.2, G.2, G.3** — document the intent. Several are deliberate
   choices whose *reasoning* just needs to reach the people who'll otherwise file them as bugs.
6. **B.5** — only with positional evidence, and only with the false-positive case tested, which is the
   mistake the current thresholds exist to prevent.
7. **D.5** — decide the 128-char truncation rather than inherit it: hash the overflow, or refuse an id
   that would truncate. Nothing misbehaves today, so this is a decision about a host-provided id.
8. **B.6** — only as a positive signal, with the recorded pages as the false-positive budget. The
   predicate it looks like is measured against them above, and fails.
9. **B.7** — only alongside typed request bodies validated against `openapi.json`; a relabelling that
    names no field just moves the guess.

## Testing notes

- **C.2 needs an explicit test** for the gateway-reports-no-destination path, documenting that it is
  fail-closed by design.
- **A.4 needs a test** distinguishing our clamp from a genuinely narrow engine page.
- **B.5 needs the false-positive case first** — a long page that *is* content and merely looks like an
  error page — before any detection is widened to catch it.
- Per-repo convention: `NODE_ENV=test`, and add/adjust tests for anything touched even unrequested.
