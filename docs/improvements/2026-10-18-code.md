# Code and correctness improvements

Correctness, attribution, and lifecycle. Capability/roadmap material lives in
[2026-10-18-functionality.md](./2026-10-18-functionality.md).

**Items here are open, or closed in place.** Each was read out of the source, not inferred. An item that
closes keeps its heading — `### X.n — closed: …` — its label and its measurements, because the evidence in
it cost a measurement to obtain, `tests/` and `docs/solutions/` cite these labels by name, and a commit
message does not carry a mutation table. An item is deleted outright only when its text was nothing but a
restatement of code a reader can open. What landed, and how, is in the commits and pull requests the closed
items name.

Labels are stable but **not reserved**: a gap means the item was fixed, not lost. Section A is now gone
entirely — A.3 and A.5 closed here, and A.1, A.2 and A.4 were already gone when this file was written —
and there is no section D, E or H, and no B.1–B.4 or G.1–G.4. B.5 and B.7 are gaps now too, both closed
on the branch named after them — one still cites its label from `tests/snapshot.test.mjs`, the other from
`src/gateway.ts`, which is exactly why the numbering does not move. Renumbering the rest would break
references to these labels that already sit in `src/` comments, commit messages and review threads — so
the gaps stay visible rather than closed. Closed **in place** rather than deleted — heading, label and
measurements kept — are C.4, C.6 and F.3, all three closed by the result-host round and its follow-ups

**On refs:** a ref here is a path and a fragment of the code it means — `` `src/gateway.ts` → `destination_unreported` ``
— and `tests/improvement-refs.test.mjs` greps every fragment out of every file it names. They used to be

is the only one of those two a reader can do anything about — so the numbers were deleted rather than
re-pointed, and this paragraph is a test now instead of a promise.

**Grouping principle:** the items are *not* ordered by severity of code smell — they're ordered by
whether a wrong answer here misleads a reader, a model, or a future maintainer. The recurring defect
in this set is not bugs; it's **statements that are slightly stronger than the code behind them.**

## B. Error attribution — faults labelled as something they aren't

### B.6 An engine that restructured organic results only is reported as having answered with nothing

`classifySerp` needs `blocks.length === 0` before it will say `parse_error`. So a *partial* restructure —
the accessibility tree still emitting `link` blocks for the engine's chrome, organic results moved to a
node type we do not read — produces links, no organics, and `empty_results`: "the engine returned no
organic results for that query", when our parser went blind. Note what is *not* wrong here: the chain
does fall through, because `empty_results` is not in `TERMINAL_CODES` (`src/engines/chain.ts` → `const TERMINAL_CODES`), so one blind
adapter is recovered and the model still gets duckduckgo's answer. Two blind adapters is a confident
wrong answer.

The obvious predicate is "links found, none of them clickable", and it was tried against the recorded
pages before being rejected here, which is why it is not in the code:

- it does not fire on the case it is for — chrome links have urls. `serp-no-results.txt` is 4 blocks,
  2 of them `https://` (Preferences, ServiceLogin), 0 organic: the exact shape, and it stays
  `empty_results`;
- it misfires on the shape duckduckgo actually serves — of 78 blocks on `serp-duckduckgo.txt`, 38 carry
  relative urls (`/`, `/compare-privacy`) and match no scheme. An engine whose organics vanished while
  its relative chrome survived would be reassigned to `parse_error`, blaming our parser for a page it
  parsed correctly. That is the false-positive family recorded in
  `docs/solutions/integration/wall-detection-must-be-structural.md`.

What would settle it is a positive signal for "this was a results list", the way `organicResults`' own
filters are positive signals — a count of *expected* node types, or a wrapper-url count, or the
`/url`→result ratio the page used to have. That is a new predicate with its own false-positive budget,
not a widening of this one.

**A recorded instance now exists, and no test reads it as a SERP.** `serp-duckduckgo-html.txt` is 26 link
blocks, every one of them carrying a `/url`, and **not one of them is absolute**: 24 are
`//duckduckgo.com/l/?uddg=<percent-encoded target>&rut=<hash>` wrappers, one is `/html/`, one is
`//duckduckgo.com/feedback.html`. Those 24 are the organic results — the destination is right there,
encoded — and every one is discarded, so `blocks.length` is 26, `results.length` is 0, and the page
reports `empty_results`: "duckduckgo returned no organic results for that query". A tree we refused to
read, blamed on a query.

**The cause is the scheme guard.** `organicResults` drops anything without a scheme before it asks what
engine it is looking at — `src/snapshot.ts` → `if (!url || !/^https?:\/\//iu.test(url)) continue;` — and a
protocol-relative value cannot match that. Measured: 0 of the file's 42 `/url` lines pass, and
`parseSerp(…, "duckduckgo")` returns 0 results. It is the same mechanism already written down for the
sibling fixture in `isChrome`'s own docstring — refused "at its scheme guard, before `isChrome` is
reached" — and it is why the relative-url false positive above bites at all.

**The cause recorded here on 2026-10-23 was wrong, and so was the fix with it.** That version said the
organics vanish "not because the parse failed" but because of an asymmetry in `isChrome` — the `google`
branch exempts a wrapper (`!isWrapper(url)`), the `duckduckgo` branch returns true for any
`*.duckduckgo.com` host — and prescribed giving the duckduckgo branch that exemption. Checked against the
function it named: false. The scheme guard rejects all 26 first, so `isChrome` is never reached for any
of them, and an exemption inside it cannot change this page. Run, not reasoned: with the exemption added
the fixture still parses to 0. It is a no-op twice over, because even where it *was* reachable it
exempts nothing — `isWrapper` only recognises `google.com/goto?url=` and `google.com/url?url=`, so a
duckduckgo wrapper is not a wrapper to it, and the exemption would need `isWrapper` generalised first.
Kept visible rather than quietly rewritten: the next reader who compares those two branches will reach
for the same cause, and should find it already tried.

**The asymmetry is real, and it is a second blocker rather than this one.** Not an inference this time —
a measurement. Make the 26 urls absolute (`https://duckduckgo.com/l/?uddg=…`, nothing else changed) and
they clear the scheme guard, and the page still parses to **0**: the host rule discards them on its own,
because a duckduckgo wrapper *is* a duckduckgo host. Reroute those same wrappers to a foreign host and
the same page parses to **10**. Two independent conditions stand between this fixture and results, and
neither one is enough alone — which is also why relaxing the guard by itself changes nothing: accept
`//…` without giving it a base and `new URL()` throws in `rawHostOf`, and `isChrome` calls a link whose host
it cannot read chrome.

**Latent, and still latent.** We request `duckduckgo.com/?q=`, not the html host — and the live recording
`serp-duckduckgo.txt` carries its organics as absolute non-duckduckgo urls, which is why 19 of them
survive today. Two recorded pages carry absolute `duckduckgo.com` urls. This one carries 15 of them — its
y.js ad proxy, /updates, /bangs, start.duckduckgo.com — every one chrome under the engine that answered,
and every one correctly dropped. The recording that motivated the ownership rule carries 10 more, 9 of them
that same footer — and that page is now refused before it is parsed at all
(`src/snapshot.ts` → `engineOwnsUrl`), which is a different finding's fix and not this one's. Neither is the failure
this item is about — a duckduckgo-host *organic* result discarded by the host rule — and nothing has been
observed failing that way; a redesign of the html host is what would
reach it, which is the exact scenario this item describes.

Three predicates measured against it first, all rejected — recorded because the item previously had no
cases to measure anything against, which is how the "links but none clickable" idea got through once:

| signal | google | duckduckgo | the html case | no-results | wall-consent |
| --- | --- | --- | --- | --- | --- |
| link blocks with a `/url` (status quo) | 10 / 18 | 78 / 78 | 26 / 26 | 2 / 4 | 3 / 3 |
| link blocks with a `/url` **and** nested text | 10 | 5 | **0** | 0 | **2** |
| `/url` lines per link block | 0.56 | 1.0 | 1.0 | 0.5 | 1.0 |

Row 2 is the one that looks right and is not: it finds 5 of duckduckgo's 19 real results, misses the case
it exists for entirely, and fires twice on a consent wall. Row 3 separates the two only by a threshold,
and scores a wall the same as a results page. All three rows were re-measured for this correction and
still hold; what was wrong above was the *cause*, not the table.

**What a fix has to carry — two changes, and neither is a one-liner.**

- A base to resolve against. `organicResults` is handed blocks and an engine name, never the snapshot's
  own url, so it has nothing to resolve `//host/…` or `/html/` *with*. Threading the page url down is the
  actual work here, and the scheme guard is not merely strict: it is what keeps `new URL()` from throwing
  on every one of these values.
- A wrapper exemption that can see a duckduckgo wrapper, i.e. `isWrapper` generalised to `/l/?uddg=` —
  not the same predicate applied to a second branch, which is the no-op above.

Both re-measured against the table with the exemption on, to prove `Preferences`/`ServiceLogin` — the 2
absolute urls of the 4 blocks in `serp-no-results.txt` — still do not become results. Measured in a
scratch tree with both changes: this fixture parses to 10 results (the 24 wrapper lines are 10 distinct
targets), and nothing else moves — `serp-google.txt` 10, `serp-duckduckgo.txt` 19, `serp-no-results.txt`
0, `wall-consent.txt` 0.

### B.8 A page that says we were blocked is reported as a search that returned one result

`tests/fixtures/serp-reddit-blocked.txt` is a recording of a refusal taken from the live gateway through
the `@reddit_search` macro, not a page written to make a point. It is 265 chars and one ref: an image, the
sentence *You've been blocked by network security. If you think you've been blocked by mistake, file a
ticket below and we'll look into it.*, and one link, `File a ticket`, to Reddit's support-desk ticket form.

Measured against it, as the engine that served it would be classified:

```
classifySerp(recording, "google")      →  { kind: "results", results: 1 }
detectWall(recording)                  →  null
classifySerp(recording, "duckduckgo")  →  { kind: "results", results: 1 }
```

The model is told the search succeeded and got one result, and the result is a link to a ticket form on a
page whose own text says access was refused.

**Two rules meet to produce it, and neither is wrong alone.** The block page has one link block, and its
`/url` is `https://support.reddithelp.com/…`, so `organicResults` admits it at its scheme guard
(`src/snapshot.ts` → `if (!url || !/^https?:\/\//iu.test(url)) continue;`) and then asks the only question
it knows how to ask — is this the engine's own page. For google, chrome is decided by host alone
(`src/snapshot.ts` → `return hostIsEngineDomain(host, rule) && !(rule.wrappers && isWrapper(url));`), and
the rule for "ours" is the engine's entry in `HOST_RULES`. `support.reddithelp.com` is not google's domain,
so a support desk on a refusal page **is** an organic result. It is the cost `isChrome`'s docstring records
as accepted when the title list was retired — a foreign host under a chrome-shaped title is a result — one
step further: here no title is needed at all, because the host rule decides alone, and a refusal page's help
desk is never the engine's host.

**`detectWall` does not catch it, and not for the reason this item first stated.** Measured: `null`. The
structural branch bails on its **first** condition — the page has no `heading` line at all, and the rule wants
exactly one at level 1 — so it never reaches the `/url` guard, which is where this item originally said the
miss came from. Deleting that guard changes nothing here: the retry-affordance condition fails too, with no
`Try Again` or `Reload` anywhere in four lines. **No page in the repo, old or new, is missed by the `/url`
guard alone.** Neither phrase list carries "blocked by network security" either, so nothing is claimed and the
page reaches the parser clean. The parser's only question is whether anything looked like a result, and one
thing did.

**The wrong verdict here is the kind the chain cannot walk away from.** `kind: "results"` is what
`src/engines/chain.ts` → `tried.push({ engine: engine.name, code: "ok", message: "served" })` credits as an
engine answering, so no second engine runs. This is the mirror image of B.6 and the opposite of its
consequence: B.6's engine is blind and says `empty_results`, which is not in `const TERMINAL_CODES`, so the
chain hops and the model still gets duckduckgo's answer. This one answers confidently and ends the search.
A parser that went blind is recovered; a refusal read as a result is not.

**Two items merged this week, and this is where both of them land.** The page has a result on the *first*
look, so `src/engines/settle.ts` → `serpWorthAnotherLook` stops the loop at once and
`src/settle.ts` → `polled: false` is what the store gate reads
(`src/tools/search.ts` → `shouldStore: () => !pagePolled`). That gate exists to hold a page that had to be
waited for out of the cache, and it waves this through, because "it answered on the first look" is the
condition it reads as finished. So the value is stored under the search key, which deliberately excludes
`n`, and served for `src/config.ts` → `serpMs: 30 * 60 * 1000`; and the stop-at-first-results rule
shipped as 1.6 means nothing looks at the page again. Measured end to end against
`tests/helpers/fake_gateway.mjs` with this recording as the served SERP: the chain records one step,
`google: ok`; the second identical query costs **0** gateway calls and reports `fromCache`. **A refusal
becomes a cached answer for half an hour, under a key that covers every result count that query is ever
asked for.**

**The recording is one instance; the class is every interstitial with a way out.** Any page hosted at an
address the asked engine owns, whose sole link points off-engine, reports as a successful search: a WAF
page with a "contact us", a rate-limit notice with a status link, a "verify you are human" screen with a
help article. The engine
argument does not save it — measured on both, and the `duckduckgo` verdict is the same, because the host
rule only decides which host counts as ours. It is squarely B-family: a fault labelled as something it is
not. B.6 covers results that exist and are missed; nothing here covered a non-result counted as one.

**Half of it is closed, by a rule that reads no text at all.** `src/snapshot.ts` → `engineOwnsUrl` now runs
in `classifySerp` before anything is parsed, and a page whose host the asked engine does not own is refused
as `empty_results` with `substituted: true` in its details. Measured against this recording at the url it
was taken at: `{ kind: "error", code: "empty_results" }`, and the chain hops instead of ending.

Two things that change, and one that does not. The model is no longer told this search succeeded with one
result, and the refusal is no longer kept — an error out of `classifySerp` is never stored
(`src/cache.ts` → `Failures are never stored.`). What is **not** fixed is the item's own ask: `detectWall`
still answers `null` for this page, so it is reported as "the engine served nothing" rather than "we were
refused". And the rule judges where the tab is, not who wrote the bytes — measured at
`tests/search-tool.test.mjs` → `B.8 as filed:`, which stays green: these same 265 chars served at a url the
asked engine *does* host still parse as one organic result, and still get cached for `serpMs`. The
predicate this item asks for is unchanged, and so is its budget.

**What a fix has to survive, and no threshold here is invented well enough to skip it.** A predicate that
reclassifies a page as a refusal is keyword or shape evidence over fetched text, which is the exact family
`docs/solutions/integration/wall-detection-must-be-structural.md` records as already having failed once —
a GitHub README that mentions a captcha was refused as a wall, and the fix was to take structure instead of
prose. It has to be measured against the recorded pages the way B.6's three candidates were, and its budget
runs in both directions: the 10 results of `serp-google.txt` and the 19 of `serp-duckduckgo.txt`, each
parsed as the engine it was recorded from, must stay results — and a real results page that also carries a
help or feedback link must not be reduced to a refusal. Whatever it decides has to be a verdict at the
classifier rather than a rule sitting above it, because that is where the two halves of this are one
defect: an error out of `classifySerp` is a code the chain hops on, and a throw is never kept —
`src/cache.ts` → `Failures are never stored.`

## C. Guard-surface correctness

The address guard is the most carefully built thing in this repo (see `CONTEXT.md`). These are the
places where it's narrower or blunter than it appears.

### C.1 `blockedHosts` cannot express path, port, or scheme

Only lower-cased host equality and `*.suffix`/subdomain matching (`matchesHostRule`,
`src/net-policy.ts` → `function matchesHostRule`). There is no allowlist at all — refuse only.

Two consequences worth stating in the docs:
- it is applied to **destinations**, so it cannot filter a blocked host out of **search results** —
  a blocked host still appears in search output;
- a rule can't express `example.com/admin` or `:8080`, which is where "block that tool's UI but not
  its docs" requests will go.

### C.2 `destination_unreported` fails *every* read, not just risky ones

When `policyCanRefuse` is true, a snapshot reporting no destination throws unconditionally
(`src/gateway.ts` → `destination_unreported`). The fail-closed choice is right and the reasoning in `CONTEXT.md` is sound —
but the blast radius is total: **a gateway upgrade that stops reporting `url` on `/snapshot` turns
all reads into errors** until the user opts out of the guard.

What this asked for was (a) a doc note and (b) the gateway's own state in the message. Both are settled,
differently. (a) — `README.md` → `Refuses to return a page` says it, and so does the refusal: the
`destination_unreported` advice line (`src/extension.ts` → `Upgrade it`) names the gateway's silence and tells
the user to upgrade it, which is the sentence this item wanted. (b) — the `/health`-style status now ships,
and is deliberately *not* attached to this code: `destination_unreported` is not on `DIAGNOSED_CODES`, and
the one fact a diagnosis could add here, that a browser is there, is already settled by a page having come
back.

What is still wanted is the version, and that is not ours to give: no gateway response reports one, so the
only version this repo holds is the recording's own (`tests/fixtures/openapi.json` → `"info"`). The user is
told to upgrade and not what they are on. §2.3 calls itself the only Tier-2 item that is a genuine
gateway-version dependency — this is a second one, and the blindness is ours.

### C.3 The stray-tab sweep's safety condition is also its blind spot

With a sibling open in flight it filters strictly by url (`src/gateway.ts` → `redirect wrapper cannot`), and the code states
plainly that "a redirect wrapper cannot" match that way. So a lost response during concurrent
activity can still leave a tab behind, reclaimed only at `session_shutdown`. Known, documented,
acceptable — recording it so nobody "fixes" it by loosening the filter, which is the dangerous
direction.

### C.4 — closed: the per-result `host` was text the page supplied, and resolution did not recompute it

Until `fix/result-host-attribution` `src/snapshot.ts` carried **two host readers with opposite trust
properties**: `hostOf(url)` — the url, parsed and normalised — which fed `detectWall` and `classifySerp`'s
message, and `hostFrom(cite, url)`, which preferred the `cite:` line, and a `cite:` line is page content.
Measured on a synthetic page served from `attacker.test`, one link block with
`- cite: https://www.google.com/official` yields
`{ url: "https://attacker.test/offer", host: "google.com" }` — and `src/tools/search.ts` → `result.host`
prints that field on every result line the model reads. Then two sites in `src/resolve.ts` replaced the url
and left the host behind, so a resolved google wrapper reported `host: google.com` while pointing at someone
else's site. The fresh open is now `src/resolve.ts` → `url: destination, resolved: true, host: resultHost(destination)`;
when this was measured it read `return { ...result, url: opened.url, resolved: true };`. The second site is
the easy one to miss — the cache hit, whose cached value is only `{ url, resolved }`, so the host never
travelled with the destination and a hit resurrected the wrapper's host against a url nobody had re-read.

**The lesson is `docs/solutions/integration/wall-detection-must-be-structural.md`'s** — host evidence has to
come off the host — applied to the one column that had been left reading page text, while
`classifySerp`'s message already printed a parsed host for exactly this class of laundered byte.

**Closed by one reader and one rule: wherever `url` is written, `host` is written in the same statement.**
`hostFrom` is deleted; `src/snapshot.ts` → `export function resultHost` (the trusted `hostOf`, plus the one
`www.` peel that is display only) is the only thing that names a host on a result; `cite` stays on the result
as the page's own text and can no longer become an attribution; and both `resolved: false` returns keep url
and host together because neither moved. `engineLabel` became `return result.host;` and its
`|| new URL(result.url).hostname` fallback was **deleted rather than normalised** — `organicResults` requires
`^https?://` and a block whose host does not parse is dropped as chrome — with that unreachability pinned
rather than assumed. `SearchResultSchema` now states where `host` and `cite` each came from, because a field
with no stated source is how this stayed plausible.

Pinned by `tests/snapshot.test.mjs` →
`C.4: a page that cites itself as Google is still reported at the address it is served from`, and — the case
that makes this a rule rather than a tuned predicate —
`tests/snapshot.test.mjs` → `C.4: a cite that tells the truth still reports the host it always did`, which
must be green before *and* after: a page quoting its own real address is unaffected, so the fix is
indifferent to the cite. Plus
`tests/search-tool.test.mjs` → `C.4: the third line of a result names the host we read off its url, and no word the page wrote about itself`,
and on the resolve side
`tests/resolve.test.mjs` → `the fixture derives host from its own url, so it cannot launder the bug it is here to catch`
(the helper used to hand-write `host: "example.test"` next to an
unrelated url, which is why no existing test could see any of this),
`a resolved wrapper reports the host of its destination, not the wrapper's`, and
`the cache hit reads the host off the destination it cached, and opens no tab to do it`.
The live half of the same claim is `scripts/verify-host-live.mjs`: one search with `resolve: false` and one
with `resolve: true` against a real gateway, printing every row and failing on any result whose host is not
the host of its own url — 10 rows, 0 lies, on the run that closed this item.

**The cost, stated rather than buried:** `src/tools/search.ts` → `const resolve = params.resolve === true;`
— resolution is opt-in — and Google serves organic links as `google.com/goto?url=…`. So on the default path
every Google result now reports `google.com`, where the page's own `cite:` used to say `github.com`. That is
true (that *is* where the link points, and `resolvable` says so) and it is strictly less useful, which is
exactly why the laundered byte survived: the honest value was the less informative one, and this chose
honesty. A caller who wants the destination asks with `resolve: true` and gets a host that followed it.

**One shape this does not fix, filed rather than guarded: C.6** — the parse-time half of it; both halves have
since been guarded, and say so under that label.

### C.5 — closed: of the three host readers outside the one normaliser, two have been routed and the third is a cache key

`src/net-policy.ts` → `export function normalizeHost` is what every rule comparison uses, and `isPrivateHost`
now calls it rather than re-typing it. Repo-wide the claim held only *nearly* when this was filed, and the
exceptions are named here so the next reader does not have to rediscover them the way the FQDN-terminator
defect was rediscovered:

- `src/tools/search.ts` → `return result.host;` — **closed with C.4**, which deleted the
  `result.host || new URL(result.url).hostname` fallback rather than normalising it. That fallback was raw
  and would have printed a terminated host had it ever become reachable, and the unreachability is pinned by
  `tests/snapshot.test.mjs` → `C.5: no result off any recorded page reaches the printer without a host to print`.
- `src/resolve.ts` → `!isWrapper(opened.url)` — **closed.** The test standing at this site was a second wrapper
  test, unanchored and shaped differently from `isWrapper`, which requires `?url=`. A destination whose url
  merely contains those bytes was judged still-wrapped; a wrapper spelled otherwise was reported
  `resolved: true` while the host field said `google.com` (see C.4).
- `src/tools/read.ts` → `new URL(url).href` — **the one left standing, on purpose**: cache key only, honest
  about it, costs a missed hit.

None of the three decided ownership, so none was a live misattribution, and only the cache key is still
outside: `isWrapper` is **exported** from `src/snapshot.ts` and is the single wrapper test, with
`src/resolve.ts` → `!isWrapper(opened.url)` as its second caller (pinned by
`tests/resolve.test.mjs` → `a destination whose url merely contains the bytes google.com/goto? is resolved, not called a wrapper`),
and `search.ts` reads no host of its own any more. The key is left as found because it is honest about being
a key, and `normalizeHost`'s own docstring in `src/net-policy.ts` records the same two routed, one left
standing — the doc and the comment cannot drift apart without one of them being wrong.

**Added while guarding C.6 (2026-11-03): that one wrapper test now asks who the url points at.** It was
`/google\.com\/(goto|url)\?url=/iu.test(url)` and nothing else — a byte test over the whole url, so
`https://mygoogle.com/goto?url=offer` was the engine's redirect. Where the caller had already established
ownership that was harmless; the two that had not were the ones that matter,

### C.6 A url whose host empties: guarded on the resolve path and, since 2026-11-07, at parse time

Found while closing C.4, and left as found until the resolve half was guarded on 2026-11-03 and this half on
2026-11-07. `resultHost` returns `""` for a url whose hostname is `.` — `https://./x` parses cleanly, so the
parse never fails, and `normalizeHost` then empties the single dot label. `isChrome` cannot drop it as chrome
either, because it is handed the **raw** hostname and `.` is not empty there. So `organicResults` used to emit
a result with `host: ""`, `engineLabel` printed `""`, and the model saw a result line whose third column was
blank. For two releases that was **pinned, not guarded** — the case then named
`C.5: the one url shape that has no host to print is named, not left a rumour` recorded the blank as a known
limit, and the ledger said the fix, when a caller ever needed one, was to drop the block at parse time: one
condition in `organicResults`, and delete the pin. That is what was done, and the pin is converted rather than
deleted — the case still names the shape, and now asserts it is gone:
`tests/snapshot.test.mjs` → `C.6: the one url shape that has no host to print is dropped, not printed as a blank column`

**Dropped, not rescued.** The other option on the table was to keep the block and fall back to the raw
hostname, which is what an earlier version of `src/tools/search.ts` → `return result.host;` did before C.4
deleted that fallback. It was rejected: a host that is nothing but dots names no one, and printing `.` in the
attribution column launders an unattributable link into a line that *reads* as attributed — the failure mode
the whole C.4 round was about, arriving from the benign direction. The distinction is measured rather than
asserted by comment: mutating the guard into that rescue (`const host = resultHost(url) || rawHostOf(url);`,
the fallback C.4 deleted, put back) reddens that one case — and the ref gate, red in every mutation this
section reports because the section cites the guard's own text — and nothing else in the suite, so the case
does discriminate dropping from printing.

**Three shapes, not one, and the second and third are why the guard reads labels off the printed field.**
`src/snapshot.ts` → `if (!host.split(".").some((label) => label !== "")) continue;` sits after the scheme
guard and before the chrome filter, and asks `export function resultHost` — the field the column prints —
rather than `hostOf`, the field the host rules use. `https://./x` is empty the first way through the dot-label
strip alone. `https://www../x` is not empty to the rules at all: normalising leaves `www.`, and it is the
`www.` peel that empties it. `https://www.../x` is the same shape with one dot too many to disappear, and
prints a bare `.` under a truthiness test. Reading labels rather than testing `!host` is the same lesson
`src/net-policy.ts` → `if (!parsed.hostname.split(".").some((label) => label !== "")) {` learned two sections
up, applied here; all three links are in the page the case parses, with an ordinary link beside them as the
control — the guard is a host rule, not this file declining to emit anything it cannot parse. Measured, each
reading is visible and each failure is the one case alone (the ref gate with it, for the reason just given):
testing `!host` instead of the labels keeps `https://www.../x`, and asking `hostOf` instead of `resultHost`
keeps both `www.` shapes.

**What is now unreachable, and what only looks that way.** No path through `organicResults` can emit a result
whose host has no non-empty label, so the blank third column is unreachable *from the parse*, and the
printer's sentence (“every result reaching this line has a host”) is now guarded at the place the host is
written rather than promised at the place it is read. What is not unreachable is the resolve half: those two
guards answer a destination the **gateway** reports, which no condition in `src/snapshot.ts` can reach, and
`src/resolve.ts` takes results from its caller, not only from this parser — so the local invariant stays, and
stays driven by the client that refuses nothing. Two things this does **not** buy, stated as measured:
the property case `tests/snapshot.test.mjs` → `C.5: no result off any recorded page reaches the printer without a host to print`
stayed green with the new line deleted, because no recorded page carries the shape — the
converted case is the only thing in the suite that can see it; and the one caller-visible change is a page
whose only organic link is such a url, which now gets `empty_results` naming the engine answering thinly
rather than a one-line result with nothing in its attribution column. That verdict is asserted in the same
case, on the distinction that matters there: the block is still a block, so the width rule is not reached and
the model is not told our parser failed.

**And one shape this still does not close, measured on 2026-11-07 rather than supposed.** The two resolve
guards ask whether a host is *empty* (the local invariant) and whether the **raw** hostname has a non-empty
label (the client's check). `https://www.../x` answers both of those favourably — its raw hostname is
`www...`, whose first label is real — and `resultHost` then leaves a bare `.` behind. Asked of
`resolveUrls` with the same client that refuses nothing the blank-column case already drives, that
destination comes back `resolved: true` with `host: "."`, and the real client's guard accepts the url rather
than refusing it. So the column is never *blank* on the resolve path and it is still not always a name. It is
recorded here, with the one shape that reaches it, rather than fixed on this round: the parse-time half was
the open item, both of its guards are pinned, and closing this one means the resolve invariant reads labels
the way the two above it do — which needs a case of its own beside
`tests/resolve.test.mjs` → `a client that reports a destination with no host is answered with a refusal, not a blank attribution column`,
not a quieter edit to a condition that case exists to pin.

**The resolve half was the one that mattered, and it is now guarded twice.** `https://./x` as a wrapper
destination came back `resolved: true` with `host: ""` and was written to the url cache as a *resolved*
destination for ten minutes, so the blank column was not a one-off answer but the answer for the next ten
minutes of a session. That also made a sentence in `src/tools/search.ts` → `return result.host;` false while
it read as a guarantee: with no fallback in the printer, "every result reaching this line has a host" was a
claim about a path nothing guarded.

Two layers, each with its own case, because a guard that lives in another module is a guard the caller cannot
see:

- **Root** — `src/net-policy.ts` → `if (!parsed.hostname.split(".").some((label) => label !== "")) {`. The
  check is now taken over the *labels*, not `!parsed.hostname`, and the difference is measured rather than
  theoretical: `new URL()` reports `.` for `https://./x` and for `https://%2e/x`, and `..` for
  `https://../x`, so the old condition was true for none of them — and `normalizeHost` strips only the one
  FQDN terminator it documents, so testing the normalised string would still have let `..` through as `.`.
  A hostname with no non-empty label names nothing and resolves nowhere: `blocked_url`, the same code the
  empty-hostname case already gave. That puts the destination the gateway reports
  (`src/gateway.ts` → `assertTabUrlAllowed(result.url, this.urlPolicy, "destination")`) in front of the same
  refusal the url we were given was always in front of, and `resolve` takes its existing unresolved path:
  `resolved: false`, the wrapper's url, the wrapper's host, and a `resolveError` naming the destination.
  Pinned by `tests/resolve.test.mjs` → `a destination whose host empties is refused by the client, and the result keeps the wrapper it came from`.
- **The local invariant** — `src/resolve.ts` → `if (destination && resultHost(destination)) {`. Whatever the
  client checked, this file may not publish `resolved: true` over a host of `""`; a destination that fails it
  falls into the refusal branch with a reason that says which half the gateway's answer broke. Pinned by
  `tests/resolve.test.mjs` → `a client that reports a destination with no host is answered with a refusal, not a blank attribution column`,
  which drives a client that refuses nothing — the fake gateway cannot be used
  for that case, because the fake is honest and this case needs a gateway that lies.

Both layers bite, and each bites alone: with the label check put back to `!parsed.hostname`, the net-policy
case `a host that normalises to nothing is no host to open, in whichever dot-shape the url spelled it` and the
end-to-end resolve case above go red together; with `resultHost(destination)` deleted from the resolve
condition, only the second resolve case goes red — the end-to-end one stays green, because the client guard
refused the destination before `resolve` ever saw it. That is what "the invariant is not inherited" means in
test terms.

## F. Cache semantics

### F.1 Eviction is insertion-order, not LRU, at 128 entries

`src/cache.ts` → `export const MAX_ENTRIES`. A re-read key keeps its original slot and can be evicted first. **Pinned as
intentional** by `tests/cache.test.mjs` — "eviction drops the oldest inserted key, not the least
used".

Deliberate is fine; surprising is not. At minimum document the choice where users can see it. If the
cache grows past a few entries of real traffic, this becomes the reason hit rates look random.

### F.2 Cache is per-pi-session — nothing shared, nothing surviving a restart

`src/camoufox-gateway.ts` → `const extensions = new Map`. Two concurrent pi sessions asking the same question each pay the
full browser round trip. Fine for a per-session design; worth an explicit statement of intent,
because "why doesn't the second session get my cache?" will otherwise read as a bug report.

### F.3 — closed: a cached refusal lost the reason the fresh path always gave

Found while guarding C.6, 2026-11-03, in the same file that item's fix touched. The cache-hit branch returned
`{ url, resolved, host, resolvable }` and nothing else, while the fresh path always set a reason —
`"stayed on the redirect wrapper"`, or the message the open threw. So inside the 30-second negative window
one wrapper answered the same question twice, differently: a reason the first time, silence the second. Not a
debug-only field — `src/camoufox-gateway.ts` → `resolveError: Type.Optional(Type.String(` puts it on the wire
the model reads, so the same wrapper at the same moment looked like two different failures depending on
whether something had asked about it in the last half minute.

**Closed by recording the reason in the refusal entry and replaying it** —
`src/resolve.ts` → `cache?.set(key, { url: result.url, resolved: false, resolveError: reason }, 30_000);` —
rather than by naming a reason in the read path. That distinction is the item, not an implementation detail:
an entry carries what the attempt *found*, and a read path that already knows what a refusal's cause must
have been testifies to something it did not witness. The fix had to be tested against that temptation, and
one of the two cases below is there for no other reason — with the read path changed to hardcode
`"stayed on the redirect wrapper"`, the wrapper case stays green (it is what the wrapper's cause *was*) and
only `tests/resolve.test.mjs` → `a cached refusal replays the reason that was recorded, not one the read path finds for it` goes red.

**Its rule has a second half, and it is the one
`docs/solutions/architecture/derived-field-must-be-written-with-its-source.md` names:** a reason belongs to a
*non*-resolution, so both success write sites clear it — the fresh open and the cache hit. The reachable door
is a caller retrying what it was told was unresolved, which is the natural thing to do with a
`resolveError`: without the clear, that retry answers `resolved: true` *and* "stayed on the redirect
wrapper", two fields of one event contradicting each other on the wire. Pinned by
`tests/resolve.test.mjs` → `an answer that carried a reason, asked again after the wrapper resolved, carries the destination and no reason`.

**What each case watches, by mutation rather than by reading** (each row is the named case that went red,
alone unless stated):

| Mutation | Cases that went red |
| --- | --- |
| refusal cached without `resolveError` | `the same wrapper asked twice inside the negative-cache window says why twice, in the same words` and the replay case above |
| read path hardcodes `"stayed on the redirect wrapper"` | the replay case **only** — the wrapper case is insensitive to it by construction |
| cache hit stops replaying the recorded reason | all three cases |
| fresh open stops clearing a carried-over reason | the retry case only |

The `resolvable` ternary beside it was left exactly as it was, mutation-tested case and all.

## G. Robustness and parsing

### G.5 Locale is not controllable

Recorded results arrived Swedish (`Sök på Google`), which is a gateway-side reality only in the sense that
nothing here translates it. Both search urls are built in this repo now — `src/engines/google.ts` →

**Two claims from the original filing, dispositioned rather than dropped.**

- *"`timeout` is built `retryable: true`, so a caller that has not attached a signal pays twice its own

- *"What has never been measured anywhere in this repo is the sentence the macro is actually there for —

  should have carried on 2026-10-26 — is the other shape: its *named unknown 2*, "the 76–134 char page that
  costs 7.2–7.9s and reports `empty_results` with no wall, **reproduced deterministically**", 6 of 6 looks
  agreeing. **That is the same page, and it has been in the record for a week with nothing done about it.**
  Re-measured 2026-11-01 and attributed: 108 chars, 1 ref, 0 organic links, `/snapshot` 7 013–7 024 ms on
  every look, byte-identical across three looks 21 s apart, and it appears on a **cold gateway profile × a

  `src/snapshot.ts` and from `/consent|captcha/` matched against the gateway's message text in
  `src/gateway.ts`, and nothing records which fired. The only instrument for any of it is
  `scripts/diagnose-wall.mjs`, which needs a live gateway. That is the follow-up; the macro's removal stands
  on the timing evidence, which was never in question.

### B.11 `extract` is the one client method still on the default retry budget, so a hung gateway costs a schema read two full deadlines

*Filed 2026-11-02 from a review of the recovered round. Read-side cost, not a search-side one — the chain
budget never sees it.*

Every gateway-bound method on the client refuses the default retry policy, and the reasoning is written down
where each one made the choice: `src/gateway.ts` → `retry: "connect-only",` appears on `preflight`, `openTab`,
`reconcileStrayTabs`, `snapshot`, `tabLocation`, `closeTab` and `deleteSession`, and `retry: "never"` on
`health` and `waitFor`. The argument they share is that a timeout has already spent the entire `timeoutMs`, so
sending it again buys a second wait and not a second chance — `read` has no chain budget to absorb that.

**`src/gateway.ts` → `async extract(params: {` is the one that does not.** It passes `userId`, `body` and
`signal` and no `retry`, and `retry` is a `RequestOptions` field a caller cannot set for itself. So it falls
to `if (attempt === 0 && gatewayError.retryable && !never && !connectOnly && !options.signal?.aborted) {`,
and `abortError` builds the deadline failure as `{ retryable: true }`. The gate reads the **caller's** signal,
not the internal deadline controller — so a per-request timeout, which is precisely the case the eight
siblings declined, is retried here: a `read` with a `schema` against a gateway that is up and answering
nothing costs **2 × `timeoutMs`** before the model is told anything.

It is reachable on the ordinary path, not a corner: `src/tools/read.ts` →
`client.extract({ userId, tabId: tab.tabId, schema: params.schema, signal: params.signal })`.

**Three things that are *not* this item.** `closeTabQuietly` takes no `retry` either, but it delegates to
`closeTab`, which sets its own policy, so it is covered. The search path is bounded twice over —
`openTab` and `snapshot` are `connect-only`, and `SEARCH_CHAIN_BUDGET_IN_DEADLINES` caps the walk — which is
why this survived: the one call site that could have noticed it is on `read`, where no budget exists to make
the doubling conspicuous. And the retry budget itself is correct as documented ("exactly one extra attempt,
and only for transient outcomes"); the defect is one method leaving the decision to a default its own
siblings rejected.

The fix is one line at the call site, not a change to the policy — but it needs the test the siblings have,
asserting that a `timeout` inside `extract` issues exactly one `POST`, or the next method added will make
the same choice by omission.
